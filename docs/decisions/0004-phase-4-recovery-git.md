# ADR 0004: Recuperação e operações Git locais explícitas

Status: **aprovado e implementado localmente na branch `feat/git-recovery-phase-4`; publicação/CI aguardam autorização**.

## Contexto e escopo

Fase 2 mantém definições, revisões, dependências, estado, eventos e evidências. Fase 3 mantém execução, tentativas e resultados de validação. Fase 4 acrescenta workspaces Git isolados, branches por workspace, checkpoints controlados e reconciliação entre SQLite e Git. Não há execução autônoma de agentes, acesso remoto, push, pull, fetch, merge/rebase, deploy ou operação de submódulo.

## Decisões consolidadas

1. **Worktree e branch:** toda tarefa autorizada a modificar arquivos versionados usa obrigatoriamente um Git worktree isolado. Cada workspace possui ID persistente e branch exclusiva própria, ligada a task/revisão/base e com ciclo de vida registrado. Tarefas que não alteram arquivos versionados não exigem worktree/checkpoint. O checkout original nunca recebe a escrita da tarefa.
2. **Ciclo de vida conservador:** workspace/branch não são removidos automaticamente se houver alteração, operação ativa/ambígua, checkpoint não reconciliado ou tarefa não terminal. Limpeza será operação explícita, registrada, com preflight de estado limpo e sem dependências; a política padrão é preservar.
3. **Checkpoint antes de conclusão:** tarefa que produziu alteração versionada exige checkpoint Git verificado para concluir. Isso é condição adicional, nunca substitui processo conhecido, validação aprovada e evidências `verified` para todos os critérios da revisão exata. Alteração posterior invalida checkpoint como precondição de conclusão. Tarefa sem mudança pode registrar operação explícita verificando HEAD/branch registrados e workspace limpo; não se cria commit vazio nem se presume que nenhuma alteração ocorreu sem essa verificação.
4. **Escopo explícito:** a tarefa/revisão autoriza uma lista explícita de paths relativos versionáveis. A lista é persistida e vinculada à revisão, não inferida por `git status` nem ampliada pelo agente. Mudança de escopo requer revisão/revalidação explícita. Validar todos os paths imediatamente antes do staging e novamente antes do commit.
5. **Staging restrito:** proibidos `git add -A` e `git add .`. Usar index privado (`GIT_INDEX_FILE` ou equivalente) e pathspec literal/NUL-safe para incluir somente paths autorizados; verificar conjunto staged exato antes do commit. Paths externos, traversal, symlink escape, arquivos operacionais/credenciais e paths não autorizados são rejeitados por padrão.
6. **Paths e submódulos:** tratar espaços, Unicode e caracteres especiais com argumentos separados, sem shell, interfaces terminadas por NUL e pathspec literal; nunca dividir ou interpolar input em comando. Detectar e recusar operações que selecionem submódulos. Em Windows, contemplar drive/UNC, separadores e colisões de case; se semântica não puder ser preservada, falhar fechado.
7. **Raiz autorizada:** toda chamada Git gerenciada verifica a identidade do worktree, `cwd`, raiz Git comum, branch e HEAD contra o registro persistido. Nenhum input pode redirecionar ação para fora do workspace autorizado. `core` consome `GitProvider` por protocolo, sem importar subprocesso/adaptador concreto.
8. **Sem efeitos remotos/destrutivos:** não executar push, pull, fetch, clone, merge, rebase ou deploy; não tocar remote, aliases/configuração/credenciais. Também não executar reset/clean, checkout destrutivo, gc/prune ou remoção implícita.
9. **Intenção e resultado:** antes de cada operação Git, gravar intenção `prepared` e reservar workspace por transação curta. Após operação, reler e verificar OID/ref/HEAD/tree/index/pathset e então gravar resultado e evento. SQLite e Git não são atômicos; nunca manter transação aberta durante subprocesso.
10. **Ambiguidade:** estados `prepared -> running -> verified | failed | unknown`. Timeout/crash depois de efeito possível vira `unknown`, bloqueia repetição automática e bloqueia novas mutações até reconciliação. Reconciliação idempotente usa fatos observados; se zero ou múltiplos resultados se encaixarem, exige decisão explícita auditável. Não desfazer commits nem repetir agente.
11. **Idempotência:** `operation_id` é único global no domínio Git e vinculado a digest canônico do tipo, workspace, task/revisão, base, pathset, política e demais parâmetros. Repetição idêntica retorna registro existente sem invocar Git; divergência é conflito; operação `unknown` não é repetida mesmo com parâmetros iguais.
12. **Checkpoint íntegro:** persistir workspace/task/revisão/tentativa, operação, base OID, commit OID, parent(s), tree OID, ref/branch, pathset e digest, ator e tempos. Relê-los após commit. FKs/constraints e verificações de domínio impedem referências cruzadas. Checkpoints Git são distintos dos checkpoints lógicos F2/F3.
13. **Concorrência:** reserva transacional SQLite e lock interprocesso por workspace; serializar também mutações a refs compartilhadas. Lock registra token não previsível, operation ID e identidade do proprietário (PID + instante de criação/identificador de processo, nunca PID isolado). Lock suspeito/orfão bloqueia; não expira otimisticamente. Revalidar identidade, HEAD e ref antes/depois de cada efeito.
14. **Migração:** SQLite v3 é backup-first e transacional, com FKs, índices únicos e eventos append-only. Operação, checkpoint e evento confirmam atomicamente o estado SQLite depois de o efeito Git ser observado; janela externa é reconciliada conservadoramente.
15. **Alterações locais:** estado dirty do checkout original não é movido nem limpo; worktree de tarefa nasce na base registrada e limpo. Alterações locais inesperadas no workspace são preservadas e bloqueiam staging/commit até reconciliação. Worktree não é sandbox: compartilha object database/refs/configuração e não impede processo com as permissões do usuário de escrever fora dele; runtime deve respeitar diretório/política efetiva da Fase 3.
16. **Plataformas:** homologação para Windows e Linux. Se caminho, lock, identidade de repositório/processo, Unicode/case ou comando não puder ser tratado com segurança, falhar antes da mutação. Submódulos são recusados nas duas plataformas.

## Contratos e sequência de operação

`WorkspaceRequest` carrega projeto, task/revision, `operation_id`, base OID, root autorizado, branch alvo e escopo de paths. `WorkspaceResult` informa workspace ID, raiz física/comum verificada, branch, base/HEAD e estado. `GitOperation` registra intenção/digest/ator/estados/evidência. `CheckpointRequest` referencia lista explícita autorizada e política; `CheckpointResult` guarda OIDs e pathset verificados. `GitProvider` fornece inspeção, criação de worktree/branch, staging isolado, commit e reconciliação; métodos remotos/destrutivos não existem no protocolo.

Fluxo: preflight read-only → reservar e gravar intenção → executar uma ação local → reabrir/inspecionar repositório e validar identidade/resultado → persistir resultado. Para checkpoint, revalidar paths antes do index e imediatamente antes do commit, validar diff staged exato, criar commit sem hooks não confiáveis quando isso for necessário ao contrato, verificar commit/tree/parent/ref/pathset e só então confirmar `verified`. Se queda ocorrer depois do efeito, recuperação compara intenção com repositório e não repete a ação.

## Matriz de testes obrigatória

- Migração v2→v3, backup SQLite consistente em WAL, rollback injetado, FKs, constraints, versão futura e preservação completa de dados F2/F3.
- Worktree em repo temporário sem remote; branch/workspace persistentes, colisões, base/HEAD divergente, alteração preexistente tracked/staged/untracked e checkout original byte a byte preservado.
- Pathnames com espaços, Unicode, colchetes, `*`, leading dash e newline quando suportado; pathspec literal/NUL; traversal, drive/UNC, case collision e symlink escape rejeitados.
- Rejeição de submódulo e de comando remoto/destrutivo; spy de invocações confirma ausência de operações proibidas e ausência de shell.
- Allowlist exata no staging/commit; alteração entre validação e staging e entre staging e commit bloqueia; nunca incluir `.agentflow/`, DB/WAL, logs, credenciais, caches, ADR legado ou arquivos não autorizados.
- Concorrência interprocesso em Windows/Linux, lock ativo/órfão/PID reutilizado, operation_id igual e divergente, execução concorrente não duplicada.
- Crash/falha antes da intenção, após intenção, durante Git, depois do commit e antes de SQLite confirmar; recuperação repetida idempotente, sem segundo commit/efeito, sem apagar/refazer.
- Checkpoint com OID/parent/tree/ref/pathset correto e tamper/change após commit; evidência declared versus verified; saída do agente zero sem validação/evidência/checkpoint não conclui.
- Regressões F1–F3, wheel instalada, Python 3.11/3.12/3.13; Codex/Docker não necessários e nenhum agente real executado.

## Riscos residuais conhecidos

Worktree não limita acesso ao repositório comum nem ao filesystem do usuário. Processo externo com o mesmo usuário pode alterar refs/objetos/arquivos entre verificações; as validações reduzem corridas, mas não criam isolamento contra adversário local. Locks e semântica de paths divergem por sistema. Hooks, filtros, atributos, configuração Git, case-insensitive filesystem e arquivos especiais podem afetar o conteúdo do commit; a implementação deverá neutralizar ou recusar configurações não auditáveis. Falhas de energia após commit podem deixar ref criada antes do registro SQLite; reconciliação conservadora pode exigir decisão humana. Git local não é backup e não protege efeitos externos do agente.

## Critérios operacionais fixados em F4-01

Os parâmetros abaixo foram fixados antes da implementação e são requisitos verificáveis. Nenhum valor flexibiliza as invariantes; valor ou identidade não verificável produz recusa segura.

## Parâmetros operacionais fixados em F4-01

- **Identidade:** `workspace_id` é UUIDv4 minúsculo sem hífens com prefixo `ws-` (35 caracteres totais). Branch exclusiva `agentflow/ws/<32-hex>`. Diretório de worktree `<git-common-dir>/agentflow/worktrees/<32-hex>` e lock `<git-common-dir>/agentflow/locks/<32-hex>.lock`, todos derivados apenas do ID validado; os worktrees e locks ficam no git common directory para não alterar status/arquivos do checkout original. Workspace conserva task ID, revisão, repo comum, base OID e branch em SQLite; não inferir identidade pelo nome do diretório.
- **Digests:** SHA-256 com prefixo textual `sha256:`. Objetos serializados como JSON UTF-8 canônico (chaves ordenadas, sem espaços, sem floats, strings Unicode NFC, sem NaN); pathset é array sem duplicatas, ordenado por bytes UTF-8 das strings NFC, cada entrada terminada por NUL antes de hash. Digest de operação abrange tipo, ator, workspace, tarefa/revisão, base, pathset, política e parâmetros integrais. Commit OID continua sendo hash Git nativo (não substituir pelo digest SHA-256 do AgentFlow).
- **Limites:** até 128 arquivos por checkpoint; caminho relativo UTF-8 NFC até 1024 bytes, componente até 255 bytes, sem absoluto/traversal; bytes agregados do conteúdo até 64 MiB. Status/saída capturados limitados a 4 MiB por comando; cada stdout/stderr de comando limitado a 1 MiB; timeout de comando Git 30 s. Exceder qualquer limite falha antes do commit, preservando os arquivos.
- **Locks:** SQLite `BEGIN IMMEDIATE` reserva o workspace; complementar com lock OS não bloqueante de um byte no arquivo persistente. Linux usa `fcntl.flock(LOCK_EX|LOCK_NB)`; Windows usa `msvcrt.locking(LK_NBLCK, 1)` sobre primeiro byte. Não há expiração baseada em relógio. O kernel libera lock após encerramento do processo; o arquivo permanece. Owner record contém token aleatório UUID, PID, início do processo, boot ID Linux ou creation FILETIME Windows, hostname e operation ID. PID sem início/token não identifica proprietário.
- **Recuperação de lock:** depois de adquirir lock não ocupado, abrir transação e reconciliar operação `prepared/running` como `unknown`, bloquear workspace e inserir evento idempotente. Nunca assumir ausência de efeito pelo lock livre e nunca repetir a chamada. Liberar workspace apenas após reconciliação explícita e registro de decisão; owner record anterior é preservado no evento.
- **Expiração/retention:** nenhuma expiração automática de workspace, branch, worktree, checkpoint, operação desconhecida ou lock file. Worktree/branch somente podem ser removidas por comando explícito de limpeza, com workspace terminal, lock exclusivo, operação reconciliada, ausência de alterações e checkpoints associados preservados no banco; limpeza recusa dirty/untracked/submódulo. Eventos/checkpoints são retidos indefinidamente nesta fase. Logs de subprocesso respeitam limites acima e são removidos apenas junto a limpeza explícita aprovada.
- **Checkpoint verificável:** commit local de um único parent igual à base registrada; ref simbólica ainda é a branch do workspace; HEAD e commit OID concordam; commit tree obtida de Git concorda com tree persistida; diff de base para commit contém exatamente o pathset aprovado; blobs/tipos correspondem à leitura validada imediatamente antes do commit; mensagem inclui trailer único `AgentFlow-Operation: <operation_id>`. Verificar também que o objeto é commit, sem gitlink/submódulo. Persistir OID, parent, tree, ref, pathset e ator. Se any check não for possível, estado `unknown`, sem novo commit automático.
- **Hooks/filtros/config executável:** comandos AgentFlow usam Git builtin em argv sem shell, `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1`, arquivo global vazio privado e hooksPath privado vazio; desativam assinatura (`commit.gpgsign=false`) e editor. Nenhuma configuração do usuário é editada. Inspecionar config efetiva do repo e attrs: recusar alias/redirecionamento, `filter.*` clean/smudge/process, `core.fsmonitor`, hooks customizados, submódulos e protocolos/remote. Atributo `filter` ou mecanismo externo não homologado recusa checkpoint. Não executar hooks/filtros por comandos Git gerenciados. Limpar variáveis `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` herdadas antes de definir valores próprios. Valores de config/ambiente não auditáveis fazem preflight falhar.
- **Identidade de commit:** nome e email do ator são campos explícitos da solicitação de checkpoint, validados e persistidos; não ler nem alterar configuração Git de usuário para preencher silenciosamente. Committer é identidade AgentFlow fixa `AgentFlow <agentflow@localhost>`; autoria original é o ator solicitado. Mensagem e trailer são produzidos pelo AgentFlow, com mensagem limitada a 1 KiB e sem caracteres de controle exceto newline.

Esses parâmetros concretizam o ADR sem relaxar worktree obrigatório, escopo explícito, recuperação conservadora ou ausência de operação remota. F4-01 está concluída após sua inclusão também na arquitetura e critérios do plano.

### Contrato versionado do escopo de escrita (F4-01)

`tasks.toml` schema v2 exige `versioned_paths` em cada tarefa; lista vazia declara que a tarefa não pode produzir alteração versionada, e lista não vazia é a allowlist literal de paths que a revisão autoriza. Schema v1 permanece legível sem alteração e equivale a `versioned_paths=[]`; mudança de plano para v2/revisão nova é explícita, nunca migração in-place. Paths não aceitam glob, curingas de expansão nem diretórios implícitos. Cada path deve ser normalizado relativo à raiz e único após NFC. O digest da definição v1 omite campo vazio para preservar compatibilidade de hash F2/F3; pathset não vazio entra no digest da nova revisão.
