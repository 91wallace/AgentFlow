# ADR 0005: Validação independente, quality gates e entrega autorizada

Status: **consolidado para revisão arquitetural; implementação ainda não autorizada**.

## Contexto

A Fase 2 mantém TOML versionado, revisões imutáveis, SQLite e evidências declaradas/verificadas. A Fase 3 separa execução de agentes e validação; a Fase 4 oferece workspaces e checkpoints Git verificados. O roadmap da Fase 5 prevê Docker opcional, isolamento configurável, builds, entrega sob política e paridade local/contêiner. Um código de saída ou declaração do agente não comprova critérios. Testes/builds executam código do projeto e devem ser tratados como execução potencialmente hostil.

## Decisões consolidadas

1. **Protocolos independentes:** `Validator`, `ValidationRunner`, `Runtime`, `ArtifactBuilder` e `DeliveryProvider` são interfaces substituíveis. `core` usa protocolos; adaptadores concretos ficam nas bordas. Validação, build, entrega e conclusão são operações distintas.
2. **TOML e compatibilidade:** só `.agentflow/spec.toml` e `.agentflow/tasks.toml` são os arquivos de definição versionados. `spec.toml` v2 acrescenta allowlist de comandos por projeto. `tasks.toml` v3 acrescenta gates. Spec v1 equivale a allowlist vazia; tasks v1/v2 equivalem a zero gates. Leitura antiga é preservada; versão futura é recusada sem escrita. IDs de comandos/gates são estáveis e removidos não são reutilizados.
3. **Allowlist e invocação:** cada gate referencia `command_id` declarado explicitamente no spec do projeto; não contém argv executável livre. A entrada allowlisted fixa identidade do executável, argv/template fechado, diretório de trabalho e versão/capacidades esperadas. Só um pedido explícito de validação executa gate; nenhum comando é inferido ou disparado pelo carregamento do TOML, conclusão ou build. Sem shell, interpolação livre, alias, wrapper ou PATH não auditado.
4. **Snapshot por execução:** cada run persiste snapshot imutável e digest canônico de tarefas/gates, allowlist, critérios, política e parâmetros efetivos. Gate result referencia revisão/digest da tarefa, checkpoint ID, commit OID, tree OID, digest do gate e ID/versão/digest do validador. Mudança de qualquer vínculo torna evidência obsoleta; resultados históricos não são reescritos.
5. **DAG e serialização:** dependências formam DAG. Ciclos, IDs duplicados, referências inexistentes/cruzadas e autorreferências são rejeitados antes de persistir run. Há uma validação ativa por projeto/banco; gates executam sequencialmente em ordem determinística, sem paralelismo nesta fase.
6. **Timeout:** 600 segundos padrão por gate, configurável por política/requisição até máximo absoluto de 3600 segundos. Valor acima do máximo falha no preflight, antes do spawn.
7. **Estados conservadores:** run: `requested -> preflight -> running -> passed | failed | inconclusive | cancelled`; gate: `queued -> preflight -> running -> passed | failed | inconclusive | cancelled`. Gate cuja dependência não terminou `passed` é `not_run`. Dependentes de falha, cancelamento, inconclusivo ou `not_run` também ficam `not_run`. Crash/timeout/erro de infraestrutura durante efeito não comprovável produz `inconclusive`; resultado desconhecido nunca aprova nem é repetido automaticamente. Nova tentativa é pedido explícito com novo `operation_id`.
8. **Agregação:** gate obrigatório falho ou `not_run` por falha ancestral torna run `failed`; sem falha, cancelamento explícito ou `not_run` por cancelamento ancestral torna run `cancelled`; sem os casos anteriores, gate obrigatório inconclusivo ou `not_run` por inconclusivo ancestral torna run `inconclusive`. Run só é `passed` quando todos os gates obrigatórios estão `passed` e vínculos foram verificados. Gates independentes podem continuar sequencialmente após falha conforme plano imutável; gates dependentes ficam `not_run`. Gates opcionais não satisfazem critérios obrigatórios.
9. **Evidências:** só `passed` verificado independentemente sobre snapshot/checkpoint vigente cria evidência `verified` para critérios explicitamente cobertos. Código de saída zero isolado, evidência declarada, gate opcional, `failed`, `inconclusive`, `cancelled`, `not_run` ou resultado stale nunca justifica conclusão. A conclusão exige ação/validação separada e todas as evidências required vigentes da revisão.
10. **Snapshot exato:** snapshot nasce exclusivamente do commit/tree do checkpoint F4, não do workspace mutável. Manifesto contém caminhos normalizados, modos Git, tipo e OID/digest de blobs, com digest raiz canônico. Leitura de objetos evita checkout/conversões e hooks/filtros; compara manifesto com tree antes/depois. Submódulos são recusados. Symlinks só são aceitos quando o target interno e a semântica da plataforma podem ser comprovados; do contrário preflight recusa. Source é read-only; output/cache fica separado e limitado. Mutação da cópia-fonte faz gate `failed`; se integridade não puder ser provada, `inconclusive`; snapshot/checkpoint de origem permanece intacto.
11. **Ferramentas/configuração:** nenhum shell, Git hooks, aliases, clean/smudge filters ou config executável é usado para materializar/validar. Executável resolvido, identidade/hash ou fingerprint, versão, argv, cwd e ambiente efetivo são registrados. Ferramenta/wrapper não auditável bloqueia gates required. Paths são relativos, normalizados e limitados; traversal, symlink escape, submódulos e artifact output fora da allowlist são recusados.
12. **Rede e credenciais:** rede desligada por padrão quando runtime pode impor e verificar. Exceção exige autorização explícita por run. Sem controle efetivo, capacidade é `unavailable`; o run requer autorização explícita para rede não confinada. Processo recebe env mínimo, nunca herda credenciais Codex/Git/user. Segredo só por referência de nome/escopo, injetado no gate necessário e nunca persistido/logado.
13. **CPU/memória e isolamento:** por gate/build default 2 CPUs, máximo 8; memória default 4 GiB, máximo 16 GiB; processos default 64, máximo 256. Aplicar quando runtime/OS suporta controle verificável; registrar solicitado versus efetivo, caso contrário `unavailable`. Política que exige recurso indisponível bloqueia preflight. Runtime local não é sandbox e não promete isolamento que o OS não fornece. Docker é opcional; quando escolhido, imagem é fixada por digest, privilégios removidos, source read-only, network off por default, mounts mínimos e quotas aplicadas/reportadas. Paridade não implica segurança ou semântica idêntica.
14. **Logs e retenção:** capturar no máximo 8 MiB stdout+stderr por gate e 64 MiB por run; armazenar no máximo 5 GiB de logs por projeto. Truncar em prefixo/sufixo com digest. Logs retidos 30 dias; snapshots 2 GiB cada/10 GiB por projeto e 7 dias após terminal; artifacts 256 MiB cada, 1 GiB por run, 10 GiB por projeto e 30 dias; diretório temporário até 4 GiB/run; total logs/snapshots/artifacts/temporários até 20 GiB/projeto. Metadados/digests/eventos permanecem. Redigir credenciais conhecidas; não herdar segredos; output bruto é sensível e redaction não detecta segredo arbitrário.
15. **SQLite e idempotência:** migração v3→v4 usa backup consistente da API SQLite antes da transação; DDL, dados, FK, migration record e `user_version` confirmam juntos. Falha reverte integralmente e preserva v3/backup; versão futura não escreve. Migração valida integrity/FKs e não restaura/repara destrutivamente de forma automática. Tabelas ligam runs, snapshots, gates, artifacts, deliveries e eventos às revisões/checkpoints. `operation_id` único com digest canônico: iguais retornam registro, divergentes conflitam. Reserva transacional e constraint impedem duas validações ativas por projeto; sem transação aberta durante subprocesso.
16. **Recovery e limpeza:** registrar intenção transacional antes do spawn e fatos/identidade depois. Interrupção entre SQLite e subprocesso reconcilia conservadoramente; não presume sucesso nem repete comando desconhecido. Após cancelamento/timeout, pedir saída graciosa por 5 s, encerrar árvore/container pela identidade verificada e confirmar término antes de apagar temporários. Após crash, validar PID+início; encerrar órfão identificado e confirmar. Se identidade/término forem incertos, manter/quarentenar diretório, marcar `unknown` e bloquear até reconciliação explícita. Temporários de preflight removidos imediatamente; snapshots/logs/artifacts seguem retenção definida; conteúdo associado a run ativo/unknown não é coletado. Reconciliar é idempotente.
17. **Build e proveniência:** Build separado de validação e conclusão; registra source commit/tree/snapshot digest, builder e versão, configuração/dependências resolvidas, SHA-256 e tamanho do artifact. Artifact fica fora do Git com paths/quota/retention; hash é recalculado ao reabrir/entregar. Proveniência incompleta ou digest divergente recusa uso.
18. **Entrega:** desabilitada por default. Cada `DeliveryRequest` exige operação explícita, `operation_id`, artifact digest validado, destino exato allowlisted e autorização vinculada àquela operação e destino. Aprovação genérica não autoriza destino diferente. Credenciais são de escopo mínimo e injetadas só no provider. Resultado é `succeeded`, `failed` ou `unknown`; efeito incerto bloqueia retry automático e exige reconciliação. Nenhuma entrega é consequência automática de gates/build/conclusão.
19. **Testes/plataformas:** testes usam providers/runtimes simulados e não executam Codex, agentes, validators externos ou deploy real. CI cobre Windows/Linux e Python 3.11/3.12/3.13; Docker permanece opcional e ausente não quebra execução local explicitamente aceita. Capacidades OS/backend indisponíveis são reportadas, não inferidas.

## Contratos definitivos

- `ValidationRequest`: `operation_id`, `validation_run_id`, projeto/tarefa/revisão e digest da definição, tentativa de origem, checkpoint ID e OIDs de commit/tree, workspace ID, digests de snapshot/gates/política, critérios, gates selecionados, timeout/recursos e runtime solicitado.
- `GateDefinition`: `gate_id` estável, versão, IDs dos critérios, `command_id` da allowlist, dependências DAG, indicação de obrigatoriedade, timeout (padrão 600/máximo 3600), política de saída/recursos.
- `GateResult`: referências à solicitação/revisão/checkpoint/gate/validador, estado, tempos, identidade/código de saída do processo, timeout/cancelamento, digest/truncagem/redação dos logs, capacidades observadas e artefatos.
- `RuntimeCapabilities`: cada capacidade usa `supported` (runtime declara que pode aplicar, ainda sem execução), `enforced` (configuração efetiva da execução foi verificada) ou `unavailable` (suporte/verificação ausente com motivo). Preflight pode aceitar `supported`; resultado de gate e evidência exigem `enforced`. Não presumir garantias.
- TOML de allowlist pode parear `container_image` fixada por SHA-256 com `container_executable` POSIX absoluto dentro da imagem. Isso é opcional para manter comandos locais existentes compatíveis; o runtime Docker nunca baixa imagem automaticamente.
- Saída JSON do comando é declaração estruturada, nunca evidência verificada por si só. Somente o gate validado, com proveniência atual e snapshot íntegro, pode criar evidência verificada; conclusão continua operação explícita separada.
- `BuildRequest/Result`: fonte e builder imutáveis; digest/tamanho/proveniência do resultado e URI operacional do artefato.
- `DeliveryRequest/Result`: digest do artefato, destino exato, autorização/política por operação, digest da solicitação, estado e resultado verificável do provider; `unknown` exige reconciliação.
- `CompletionRequest`: IDs de evidências verificadas para cada critério obrigatório e revisão/checkpoint vigente; gate aprovado não produz conclusão por si só.

## Parâmetros F5-01 e perfis fixados

Todos os valores são limites por projeto, salvo limites explicitamente por gate/run; `MiB`/`GiB` são potências de 2. Nova operação falha antes do spawn ao exceder quota, sem remover conteúdo ainda retido. Quotas: logs 8 MiB/gate, 64 MiB/run e 5 GiB/projeto, retenção 30 dias; snapshot 2 GiB/cada, 10 GiB/projeto, retenção 7 dias terminal; artifacts 256 MiB/cada, 1 GiB/run, 10 GiB/projeto, retenção 30 dias e pin até entrega terminal; temporários 4 GiB/run; total storage de payload 20 GiB/projeto. Timeout 600 s padrão/3600 s máximo; CPU 2 default/8 max; memória 4 GiB default/16 GiB max; processos 64 default/256 max por gate/build.

Perfil `local-explicit`: obrigatório pedido explícito, argv allowlisted sem shell, ambiente mínimo, timeout, process identity, output limitado, diretório temporário privado, conferência do snapshot antes/depois e tentativa de terminar árvore. Rede, read-only forte e quotas OS são capabilities opcionais; reportar `unavailable`, nunca fingir enforcement. Política que exige capability indisponível bloqueia. Rede sem controle efetivo exige autorização explícita para rede não confinada. Perfil `docker-isolated`: Docker/capabilities verificadas, imagem por digest, não privilegiado, sem host network/socket, mounts mínimos (source read-only/output quota), rede none, CPU/memória/PIDs/timeout e encerramento do container. Incapacidade de provar qualquer controle obrigatório bloqueia preflight; sem fallback local silencioso. Docker não é obrigatório.

Após cancelamento/timeout, encerrar processo/árvore ou container e verificar término antes de remover diretório gravável temporário. Após crash, reconciliar identidade PID+início; órfão identificado pode ser terminado e precisa ter término confirmado. Identidade/resultado incerto implica quarentena e bloqueio, sem limpeza enquanto puder estar em uso. Somente temporários de preflight são removidos imediatamente; workspace descartável é limpo após término/reconciliação, snapshots e artifacts obedecem retenção. Segredos não são herdados; segredo excepcional exige referência/escopo e autorização explícita, valor apenas em memória e redigido no output. Redator falho descarta output bruto e marca a validação inconclusiva quando output é necessário.

No Windows, Job Objects são capability possível para CPU/memória/PIDs/process tree; rede isolada e ACL de read-only para processo sob o mesmo usuário não são presumidas. No Linux, cgroup v2/controller delegado é necessário para quotas de árvore; network namespace eficaz precisa ser demonstrado. Sem capability detectada, status `unavailable`; o perfil bloqueia se obrigatória. Docker Desktop/Windows container também passa preflight de capabilities; o nome do backend não prova isolamento.

## Ordem definitiva F5-01 a F5-10

F5-01 fixa limites/capacidades operacionais; F5-02 define contratos; F5-03 versiona TOML/allowlists; F5-04 migra SQLite v4; F5-05 cria snapshots imutáveis exatos; F5-06 implementa scheduler sequencial/estados/recuperação; F5-07 integra runtimes local/Docker e validadores; F5-08 integra evidências/conclusão; F5-09 registra proveniência de builds e entrega com autorização separada; F5-10 completa CLI, matriz de testes, documentação, pacote e CI. Dependências e critérios estão em `docs/implementation-plan.md`.

## Gate de F5-01

F5-01 está documentalmente fixada pelos parâmetros e perfis acima. Antes de escrever F5-02 a F5-10, deve ser verificada em revisão de implementação: unidades/quotas têm teste de limite e overflow, capacidade `unavailable` impede alegação de enforcement, regras de limpeza preservam runs desconhecidos e perfis rejeitam ausência de requisitos obrigatórios. Não alterar os números sem revisão explícita deste ADR.

## Riscos residuais

Runtime local sob o mesmo usuário não isola processos do filesystem/rede sem suporte OS comprovável; Docker ainda depende de daemon/kernel/imagem/configuração e não neutraliza código malicioso em toda circunstância. Semântica de symlink, ACL, case, process groups, resource limits e signals difere entre Windows e Linux. Redaction não encontra todos os segredos; build/test podem ser não determinísticos; provenance comprova entradas/outputs, não correção lógica. Entrega pode produzir efeito remoto irreversível antes de resposta perdida, exigindo operador para reconciliar. SQLite backup/migração e retenção requerem espaço e procedimento de recuperação.
